## 0. Extraction conventions and caveats

The scan is OCR-degraded. This file normalizes the notation while keeping the report's own meta-notation:

- `::=` — production
- `{A | B | C}` — one of the alternatives **must** appear (mandatory choice)
- `[A | B]` — optional (may appear or be omitted)
- `X•••` — one or more repetitions of `X`
- `{,• X•••}` — one or more repetitions of `X`, each preceded by `,` (comma-separated list)
- `{.• X•••}` — ditto with `.` (dot-joined, used for name qualification)

Notation variables are lowercase hyphenated names; notation constants are PL/I keywords (uppercase) and symbols. Words printed in production rules *not* separated by whitespace compose single notation constants (e.g. `PROCEDURE` is one word, `GO TO` is two).

Legibility markers:

- ⚠ = OCR of this rule was partially illegible; reconstruction is best-effort, sometimes inferred from context. Details in the rule's footnote.
- Semicolons `;` at statement ends were restored on rules where the OCR dropped them; their presence is confirmed by rules that preserved them (EXIT, STOP, CALL, record-I/O, `SYSTEM ;`) and by the multiple-closure prose ("between 'END' and ';'").
- `¬` is the PL/I not-prefix. The OCR renders it as `,` / `-.` / `=f` / `•` in various places (confirmed by §2.3.3 where `¬ ::= NOT`).
- Original rule numbers `(1)`–`(151)` are preserved for cross-referencing with the printed report.

## 1. Notation semantics (report §2.1)

Given `V ::= S1 T1 | S2 T2 | … | Sn Tn`, the extended forms are:

1. `V ::= {T1 | T2 | … | Tn} S` — mandatory choice (may also be used with n = 1).
   Example: `goto-statement ::= { GOTO | GO TO } reference ;`
2. `V ::= S1 [T1 | … | Tn] S2` — optional.
   Example: `return-statement ::= RETURN [ ( expression ) ]`
3. `V ::= U•••` — one or more repetitions of `U` (recursive closure).
   Example: `integer ::= digit•••`
4. `V ::= S1 T1 [ {T2 | … }••• ] S2` — optional repetition.

Comma-dot form: `V ::= {,• X•••}` stands for `X ( , X )•••`.
Example: `declarationlist ::= {,• declaration•••}` for `DECLARE A, B, C;`.

### Meta-syntax of the notation itself (report §2.2, condensed)

```
<prod-rule> ::= <not-var> <definition>
<definition> ::= <sequence> | <sequence> | <definition>
<sequence>   ::= <unit> <sequence> | <unit>
<unit>       ::= <not-var> | { <definition> } | [ <definition> ] | <unit>••• | <not-const>
<not-var>    ::= <sm-letter> <not-var> | <sm-letter> - <not-var> | <sm-letter>
<not-const>  ::= <PL/I-symbol> <not-const> | <PL/I-symbol>
```

Notation variables are sequences of small letters and hyphens; notation constants are PL/I symbols.

## 2. Generation of a concrete program text (report §2.3.1)

An implementation must provide production rules for the three implementation-dependent notation variables: `external-option`, `io-option`, `extralingual-character`. Generation proceeds in four steps:

1. Replace from `program` using the higher-level rules (§3.1). Continues until no higher-level rule is applicable. Result: a text of "PL/I words" (§5). Words not separated by whitespace compose single notation constants.
2. Insert `space` between adjacent non-delimiters (mandatory); optionally elsewhere, including after the last word. The 24 delimiter words are:
   `( ) , . : ; = + - * / ** || & | ¬ < > >= <= ¬> ¬< ¬= ->`
   (⚠ OCR of the delimiter list partially legible; quote-handling for `'` not fully recoverable.) All other words are non-delimiters. `space` rules are (149).
3. Replace keywords — possibly by their abbreviations (§3.1 of this file) — then apply the lower-level rules (§3.2).
4. Split all notation constants into their single symbols. Result: a text of the 60-character PL/I alphabet:
   `A–Z 0–9 blank = ¬ + - * / ( ) , . ' : ; # @ $ & | < > % _ ? !`
   (⚠ OCR of the printed alphabet partially legible; set reconstructed from §2.2/§2.3.1 symbol lists and symbol usage in the grammar.)

### 3.2 Multiple closure of blocks and groups (report §2.3.2.2)

After the four generation steps (including abbreviations), a part of the program text is a *compound* if it could have been generated by:

```
compound     ::= compoundhead [ compound ] compoundend
compoundhead ::= [ prefixlist ] { [ labellist ] BEGIN [ OPTIONS ( {,• external-option•••} ) ]
               | entry-namelist { PROC | PROCEDURE } [ parameterlist ]
               | [ labellist ] DO [ do-specification | WHILE ( expression ) ] }
               [ sentence••• ]
compoundend  ::= [ prefixlist ] [ labellist ] END [ procedure-optionslist ] ;    ⚠
```

⚠ `compoundend`: the scan prints `[ procedure-optionslist ]` after `END`; the intended placement (after `[parameterlist]` in the procedure alternative, mirroring rule 2) is possible. Verify against print.

Before the rightmost semicolon of a compound (between `END` and `;`), one identifier of the `labellist` or `entry-namelist` of the appertaining compoundhead may be inserted (`END identifier;`).

If a compound has such a compoundend (`END identifier;`) where `identifier` does **not** occur in the labellist/entry-namelist of its compoundhead, an immediately preceding compoundend with no prefix- or labellist may be omitted.

### 3.3 Programs in the 48-character set (report §2.3.3)

It is possible to write programs in the 48-character set:
`A–Z $ 0–9 blank + - * / ( ) , . ' : ;` plus `= ¬` (⚠ printed list partially legible).

1. From the rules for `letter`, `alphanumeric-character`, `string-character`, `comment-symbol`, the following 12 symbols must be deleted:
   `@ # ¬ & | < > ? % _ !` + 1 further symbol (⚠ list partially legible).
2. These PL/I words are handled as notation variables and replaced by the higher-level rules:

   | Word | Replacement | Word | Replacement |
   |---|---|---|---|
   | `¬` | NOT | `<=` | LE |
   | `&` | AND | `¬>` | NG |
   | `\|` | OR | `¬<` | NL |
   | `>` | GT | `¬=` | NE |
   | `<` | LT | `\|\|` | CAT |
   | `>=` | GE | `->` | PT |

   (Report prints "13 PL/I words"; 12 mappings visible in scan.)
3. The 12 letter sequences `NOT AND OR GT LT GE LE NG NL NE CAT PT` are reserved words: no identifier may finally be replaced by any of them.
4. In the final text, each colon `:` is to be replaced — (a) when immediately following a dot, and (b) otherwise — by means of production rules for `space` (⚠ the two replacement rules themselves are lost in the OCR).
